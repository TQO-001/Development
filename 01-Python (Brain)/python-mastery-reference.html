Closures A closure is created when a nested function references variables from its enclosing scope, and Python keeps those variables alive in the function's __closure__ even after the outer function has returned. Each call to the outer function creates a fresh, independent set of captured variables, so closures preserve state between calls without needing a class. This is the exact mechanism decorators rely on to wrap functions, and it's how you build counters, memoizers, or config factories without instantiating a full object. Reach for a closure when you need lightweight state carried across calls but don't want the overhead of a class. closure, free variable, enclosing scope
Decorators⚠ FOCUS A decorator is a higher-order function that takes a function as an argument, wraps it in another function that adds behavior, and returns the wrapper — @decorator is sugar for func = decorator(func). Because the wrapper replaces the original function's identity, always apply functools.wraps inside so the original name, docstring, and signature survive for introspection and debugging. Use decorators for cross-cutting concerns that would otherwise be copy-pasted into every function — logging, timing, retries, permission checks, caching. @lru_cache is the built-in example: it transparently memoizes results, turning expensive repeated calls into O(1) lookups after the first run. @wraps, functools, higher-order fn
Generators⚠ FOCUS A function containing yield becomes a generator function; calling it doesn't run the body immediately — it returns a generator object that executes lazily one yield at a time, suspending and resuming its exact local state between each value produced. This is fundamentally different from a function that builds and returns a full list, since nothing is computed until you actually iterate. Use generators anywhere you're processing a sequence that's large, infinite, or expensive to fully materialize — reading gigabyte log files line by line, streaming API results, lazy pipelines with itertools. The payoff is O(1) memory instead of O(n): a little per-call overhead in exchange for handling datasets that would never fit in memory as a list. yield, StopIteration, gen expr
Iterators Any object implementing __iter__ (returning an iterator) and __next__ (returning the next value or raising StopIteration) satisfies the iterator protocol — what for loops, comprehensions, and * unpacking all rely on. Generators are the easiest way to create one, since yield auto-generates this machinery for you. Matters when a custom object needs to behave like a native sequence in a for loop, or when debugging why something is "iterable" but not "an iterator" — an iterable can be looped over repeatedly, an iterator is consumed once. This distinction is what causes the classic bug of reusing an already-exhausted generator. iterable protocol, iter(), next()
Dunder Methods Double-underscore methods are Python's hook system — the interpreter calls them implicitly in response to operators and built-ins, e.g. str(obj) calls __str__(), obj() calls __call__(), and obj.missing triggers __getattr__() only when normal lookup fails. This is operator overloading: you're not overriding syntax, you're implementing the interface the syntax already expects. Implement these to make a custom class integrate naturally with Python's ecosystem — printable with print(), comparable with ==, iterable in a for loop, usable as a dict key via __hash__/__eq__. This is what separates a plain data bag from a class that feels like a first-class Python citizen. magic methods, operator overload
Context Managers⚠ FOCUS The with statement calls __enter__() on entry (its return value binds after as) and guarantees __exit__() runs on the way out — even after an exception — because __exit__ receives the exception info and can suppress or propagate it. @contextmanager from contextlib lets you write this as one generator function with a single yield instead of a class with two methods. Use context managers for anything that must be cleaned up reliably: closing files, releasing locks, committing/rolling back DB transactions, restoring global state after a test. The guarantee that cleanup runs on every exit path — success, early return, or exception — is what makes resource leaks preventable. with, contextlib, resource mgmt

Inheritance & Polymorphism⚠ FOCUS Inheritance lets a subclass reuse and extend a parent's attributes and methods; polymorphism means different classes can be used interchangeably as long as they implement the same interface — Python favors duck typing over strict interface declarations. super() is the correct way to call a parent's implementation from an override, and it cooperates correctly with multiple inheritance via the MRO rather than hard-coding a parent's name. Use inheritance when a subclass genuinely is a specialized version of the base (an "is-a" relationship) — sharing code alone is better solved with composition. Polymorphism is what lets a function accept "any object with a .read() method" and work correctly whether it's a file, a socket, or a test mock. override, super(), duck typing
Encapsulation⚠ FOCUS Python has no true private members — a single leading underscore (_name) is convention meaning "internal, don't touch," while a double leading underscore (__name) triggers name mangling to _ClassName__name, mainly to avoid accidental collisions in subclasses rather than to enforce real privacy. @property is the idiomatic way to add validation or computed logic to attribute access while keeping plain dot-syntax for callers. Use encapsulation to protect an object's internal invariants — e.g. ensuring a balance can never be set negative directly, only adjusted through a controlled method. Reach for @property specifically when you need logic behind what looks like plain attribute access, without breaking every existing call site. name mangling, property
Multiple Inheritance / MRO⚠ FOCUS When a class inherits from more than one parent, Python builds a Method Resolution Order — a single linear list of classes — using C3 linearization, guaranteeing an order that respects each parent's own inheritance chain. You can inspect it directly via Class.__mro__, and a chain of super() calls walks this list rather than jumping straight to "the" parent, which is what makes cooperative mixins work correctly. Matters most with mixin classes — small classes designed purely to be combined with others to add one capability (e.g. a LoggingMixin). Understanding MRO is essential for debugging "why did my parent's method run instead of my mixin's," a notoriously confusing bug class without knowing the resolution order Python actually computed. mixin, super() chain
SOLID Principles Five design guidelines, not language features: Single Responsibility (one reason to change), Open/Closed (extend via new code, not edits to tested code), Liskov Substitution (a subclass must be usable anywhere its parent is), Interface Segregation (many small interfaces beat one large one), Dependency Inversion (depend on abstractions, not concrete implementations). None are enforced by the interpreter — they're architectural discipline you apply deliberately. Apply SOLID thinking when a codebase will grow or be maintained by more than just you — it specifically targets the ripple effect where one change breaks unrelated code. It matters less for a one-off script, more as soon as there are tests, multiple contributors, or a long lifespan involved. SRP, OCP, LSP, ISP, DIP
Creational Patterns Control the process of object instantiation itself. Singleton restricts a class to one shared instance (often checked in __new__); Factory centralizes object creation behind a function or method so calling code doesn't need to know the concrete class it gets back. Use Singleton sparingly — for genuinely single shared resources like config or a connection pool — since overuse makes testing harder via hidden global state. Use Factory when the class to instantiate depends on runtime conditions, so callers depend on an abstraction instead of a long if/elif chain of constructors. Singleton, Factory
Structural Patterns Compose objects and classes into larger structures while keeping them flexible. Adapter wraps an object with an incompatible interface so it matches what your code expects, without modifying the original. Facade sits in front of a complex subsystem and exposes one simple, unified interface to callers. Reach for Adapter when integrating a library or legacy code whose signatures don't match your codebase — it isolates the mismatch in one place instead of scattering conditionals everywhere. Reach for Facade when a subsystem (e.g. a multi-step payment flow) has grown complex enough that most callers only need one entry point. Adapter, Facade
Behavioral Patterns Govern how objects communicate and delegate responsibility. Observer defines a one-to-many dependency: when a "subject" changes state, registered "observers" are notified automatically without the subject knowing their concrete types. Strategy defines a family of interchangeable algorithms behind a common interface, swappable at runtime. Use Observer for event-driven systems — UI updates, pub/sub messaging, side effects triggered by a state change. Use Strategy when several ways exist to perform the same task (sorting, pricing, validation) and you want to choose between them without a long conditional chain in the caller. Observer, Strategy

Big O Notation Describes how runtime or memory use grows as input size n grows, focusing on the dominant term and ignoring constants — O(n) and O(2n+5) are both just "linear." It's a worst-case (or average-case) bound, not a stopwatch measurement, letting you reason about scalability independent of hardware. You need this the moment data size is unknown or could grow — an O(n²) algorithm fine on 100 items can become unusable at 100,000. Use it to compare algorithm choices before writing code, and to explain in review exactly why one approach will or won't scale. O(1) O(n) O(log n) O(n²)
list A dynamic array — a contiguous memory block that over-allocates extra space so most .append() calls are O(1) amortized, but inserting/deleting at the front or middle is O(n) since every subsequent element shifts. Indexing by position is O(1), direct memory address arithmetic. Use as the default sequence for anything mostly appended to and iterated over. Avoid repeatedly inserting/removing from the front of a large list — reach for collections.deque instead, O(1) at both ends. array, amortized append
dict / set Both built on hash tables — a key's hash() determines which "bucket" it lands in, giving O(1) average lookup/insert/delete regardless of size, at the cost of O(n) worst-case with many collisions. Fundamentally different from a list's O(n) linear scan. Reach for these whenever checking "does this exist" or "have I seen this before" — deduplicating, counting, looking up by ID. Rule of thumb: if you're calling in on a list inside a loop, you almost certainly want a set instead. hash table, collision
tuple Like a list but immutable — once created its contents can't change, so Python can compute and cache its hash once, making it usable as a dict key or set member (something a mutable list never can). Immutability lets the interpreter make internal optimizations since contents won't shift underneath it. Use when data has a fixed, meaningful structure (a coordinate pair, an RGB triple) and you want to signal "don't mutate this." Use specifically as a dict key when keying on a combination of values, like an (x, y) grid position — a list could never do this. immutability, hashable
Trees / Graphs / Tries / Linked Lists Pointer-based structures where nodes hold references to other nodes rather than living in one contiguous block. Trees organize nodes hierarchically; graphs generalize to arbitrary many-to-many connections; tries organize nodes by shared sequence prefixes (usually strings); linked lists chain nodes one after another, giving O(1) insertion at a known position without shifting. Trees for hierarchies (file systems, org charts) and keeping sorted data searchable in O(log n). Graphs for networks (social graphs, road maps) traversed with BFS/DFS. Tries for fast prefix search (autocomplete). Linked lists specifically when you need frequent mid-sequence insertion/deletion without list's shifting cost. BFS, DFS, node, edge
Divide & Conquer Recursively splits a problem into smaller independent subproblems of the same type, solves each (often recursively, to a trivial base case), then combines the sub-results into the final answer. Efficiency usually comes from a cheap combine step relative to the size reduction achieved by splitting. The paradigm behind merge sort and binary search — O(n log n) or better, versus naive O(n²) or O(n). Reach for it whenever solving smaller versions of a problem then merging is easier or faster than solving it directly. recursion, merge sort
Greedy Algorithms Builds a solution step by step, choosing whatever looks best right now, never reconsidering that choice later — no backtracking, no exploring alternatives. Fast, but only produces the true optimal answer when the problem has "optimal substructure," meaning a locally optimal choice guarantees a globally optimal one. Use for problems like activity scheduling or making change with standard coin denominations, where the greedy choice is provably optimal. Be cautious applying greedy logic where it isn't provably correct (certain knapsack variants) — it runs fast but may silently give a wrong answer. scheduling, coin change
Dynamic Programming Solves problems with overlapping subproblems by storing (memoizing) each subproblem's result the first time it's computed, so later requests for the same subproblem are O(1) lookups instead of recomputation. Can be top-down (recursion + cache — what @lru_cache automates) or bottom-up (iteratively filling a table from the smallest subproblems up). Reach for DP when a naive recursive solution would recompute the same subproblem exponentially many times — Fibonacci, the knapsack problem, edit distance. The signal to look for: if your recursion tree keeps hitting the exact same inputs, DP turns exponential blowup into polynomial time. memoization, tabulation

GIL CPython's Global Interpreter Lock ensures only one thread executes Python bytecode at any instant, even on a multi-core machine — threads take turns, switching periodically or when a thread performs blocking I/O. This keeps CPython's internal memory management simple and thread-safe, but means Python threads don't get true parallel execution of Python code. Explains a common surprise: adding threads to a CPU-bound task (heavy number crunching) won't make it faster, and can even slow it slightly via context-switching overhead. Essential background before choosing between threading, multiprocessing, or asyncio. Global Interpreter Lock
Multithreading threading runs multiple threads within the same process, sharing memory — cheap to create, great for tasks that spend most time waiting (network/disk I/O), since a blocked thread releases the GIL and lets another run. Shared memory means explicit synchronization (Lock, RLock, Semaphore) is needed to avoid race conditions. Use for I/O-bound workloads — many concurrent API calls, scraping multiple pages, simultaneous file reads — where the bottleneck is waiting on external systems, not computation. Wrong tool for CPU-bound work because of the GIL constraint above. Thread, Lock, race condition
Multiprocessing multiprocessing spins up entirely separate OS processes, each with its own interpreter and memory space, so each has its own GIL and true parallel execution across cores is possible. Processes can't directly share memory — data must be explicitly serialized (pickled) and passed via queues or pipes, and startup is heavier than a thread's. Use for CPU-bound workloads needing real parallel speedup — image processing, numerical computation, heavy data transformation across cores. Inter-process communication overhead means it's not worth it for lightweight, frequent, small tasks — that's where threading or async wins. Process, Pool, IPC
Async / Await⚠ FOCUS asyncio runs a single-threaded event loop managing many coroutines cooperatively — a coroutine (async def) runs until it hits an await on an I/O operation, voluntarily yielding control back to the loop, which runs another ready coroutine. Nothing is preemptively interrupted; coroutines cooperate at await points, which is why a long CPU-bound calculation inside one blocks the entire event loop. Use when managing thousands of concurrent I/O-bound connections with minimal memory overhead — web servers, API gateways, chat apps — since coroutines are far lighter than OS threads. Not a substitute for multiprocessing on CPU-bound work, since an await point never appears in pure computation and the loop just stalls. coroutine, await, event loop

Testing & Mocking pytest/unittest let you write functions asserting expected vs. actual output, running your codebase's behavior automatically instead of manually clicking through it. unittest.mock replaces a real dependency (a DB call, an API request, the current time) with a fake object returning exactly what you tell it, so a test verifies logic in isolation from things outside your control. Write tests before or alongside any code you'll change again — they make refactoring safe instead of terrifying, since you find out immediately if something broke. Mock anything slow, non-deterministic, costly, or network-dependent so the suite stays fast and reliable. fixture, assert, patch
Type Hinting The typing module lets you annotate variables, parameters, and returns with expected types (List[int], Optional[str], custom Protocol classes), which the interpreter does not enforce at runtime — hints are purely for humans and tools. A static checker like mypy reads these and flags mismatches before you ever run the code. Add hints to any function whose inputs/outputs aren't obvious from its name, and to any public API others call — it turns the signature itself into documentation. Run mypy in CI on a growing codebase to catch an entire class of bugs before runtime. static typing, mypy
Metaprogramming Classes are themselves objects created by a metaclass (type by default), so you can customize how classes get built via a custom metaclass or __init_subclass__ — both intercept and modify class creation itself, not just instance creation. This is code that writes/modifies code at the class-definition level, run once when the class statement executes. Advanced and rarely needed in everyday code — reach for it building frameworks or libraries, like an ORM auto-registering every model subclass, or a plugin system validating that subclasses implement required methods. If you want metaclasses for typical application code, a decorator or mixin usually solves it with far less complexity. metaclass, __new__
Clean Code Standards PEP 8 is Python's official style guide covering naming, whitespace, line length, and layout. Linters like Ruff/Flake8 statically analyze code against these (and other) rules without running it, flagging violations and potential bugs. Formatters like Black automatically rewrite code to a consistent style, removing debate about formatting. Run a linter and formatter as part of normal workflow (on save, or a pre-commit hook) so style issues never reach code review — freeing reviewers to focus on logic. Consistency matters most the moment more than one person touches a codebase, or you return to your own code months later. linting, formatting

DB Integration & ORMs An ORM like SQLAlchemy maps Python classes to database tables and instances to rows, translating method/attribute access into SQL behind the scenes, and manages a connection pool so the app reuses connections instead of opening a new one per request. Migrations (e.g. Alembic) track schema changes as versioned, applyable scripts so the database evolves alongside the code. Use an ORM to avoid raw SQL strings scattered through the codebase, and to get protection against SQL injection by default via parameterized queries. Learn to read the SQL your ORM actually generates once the app scales — an innocent-looking query can quietly generate a slow N+1 query problem that only shows up under real load. ORM, migrations, conn pool
API Design RESTful APIs organize functionality around resources (nouns) accessed via HTTP verbs (GET, POST, PUT, DELETE); GraphQL exposes one endpoint where the client specifies exactly which fields it needs. FastAPI builds on Python type hints to validate incoming data automatically and generate interactive OpenAPI docs for free, and is async-native from the ground up. Choose REST for simplicity and wide tooling support when data maps cleanly onto resources; choose GraphQL when clients need flexible, varying data combinations and you want to avoid over/under-fetching. FastAPI is a strong default for new Python backends given the combination of speed, validation, and docs with very little boilerplate. REST, GraphQL, OpenAPI
Automation & Scripting CI/CD pipelines (e.g. GitHub Actions) run a defined sequence — install deps, test, lint, build, deploy — automatically on push or PR, via YAML config living in the repo itself. ETL and general automation scripts apply the same idea to data/ops tasks: replace a manual, repeatable human process with code that runs identically every time. Set up CI to run your test suite and linter on every push so broken code is caught before it merges, not after deploy. Reach for automation anywhere you find yourself doing the same multi-step manual task more than twice — the scripting time pays back quickly and removes human error. pipeline, cron, workflow
